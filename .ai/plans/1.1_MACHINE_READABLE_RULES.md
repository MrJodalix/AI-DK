# AI-DK 1.1 – Plan: Maschinenlesbare Regeln

Status: **Planung** (noch nicht implementiert)  
Basis: Framework **1.0.x** · Markdown bleibt kanonisch  
Datum: 2026-07-29

---

## Ziel

AI-DK um kompakte, maschinenlesbare Regeldateien erweitern, die Agenten und Tools konsistent auswerten können — **ohne** eine zweite Wahrheitsquelle neben den Markdown-Core-Dokumenten.

---

## Geltungsbereich

In Scope für 1.1:

- Verzeichnis `.ai/rules/`
- YAML-Dateien als **Ableitung** aus dem Core
- Abgleichprozess Markdown → YAML
- Kurze Spezifikation des YAML-Schemas
- Aktualisierung README, VERSION, CHANGELOG, Testszenarien

Nicht in Scope für 1.1:

- Profiles (`2.0`)
- Tool-Extensions (Cursor/Copilot-spezifische Adapter)
- Automatische Codegenerierung aus YAML
- Ersetzen der Markdown-Dokumente

---

## Grundprinzipien

1. **Markdown ist kanonisch** — bei Konflikt gewinnt `.ai/0x_*.md`.
2. **YAML ist abgeleitet** — keine Regel nur in YAML.
3. **Kompakt und stabil** — IDs und Schlüssel versionieren, Texte kurz halten.
4. **Rückwärtskompatibel** — Projekte ohne `.ai/rules/` bleiben mit 1.0 Core gültig.

---

## Geplante Struktur

```text
.ai/
├── 00_PROJECT_CHARTER.md          # kanonisch (unverändert Rolle)
├── … 
├── 11_VERSION.md
├── rules/
│   ├── README.md                  # Schema, Sync-Pflicht, Konfliktregel
│   ├── coding.yml
│   ├── testing.yml
│   ├── git.yml
│   ├── architecture.yml           # aus Charter/Workflow/Behavior verdichtet
│   ├── documentation.yml
│   ├── security.yml
│   ├── release.yml
│   └── version.yml
└── tests/
    ├── SCENARIOS.md
    └── RESULTS.md
```

Hinweis: Dateischnitt kann beim Umsetzen leicht angepasst werden; Mapping auf Core-Docs muss dokumentiert sein.

---

## Vorgeschlagenes YAML-Minimalmodell

Pro Datei (Konzept, noch kein finales Schema):

```yaml
aidk: "1.1"
source: "03_CODING_STANDARDS.md"   # kanonische Quelle
rules:
  - id: CS-001
    severity: must          # must | should
    summary: "…"
    refs: ["03_CODING_STANDARDS.md#…"]
```

Verbindlich festzulegen bei Umsetzung:

- erlaubte `severity`-Werte
- ID-Schema (`CS-`, `TS-`, `GIT-`, …)
- ob `should` = Empfehlung aus den Markdown-Docs

---

## Umsetzungsschritte (nach Freigabe der Implementierung)

1. Schema in `.ai/rules/README.md` festschreiben  
2. Erste Dateien aus bestehenden Docs ableiten (`coding`, `testing`, `git`, `security`)  
3. Restliche YAML-Dateien nachziehen  
4. Sync-Checkliste: „Markdown geändert → YAML prüfen“ in `07_DOCUMENTATION.md` / AI-DK-TODO  
5. Framework-Szenario ergänzen oder S1–S6 um YAML-Konsistenz erweitern  
6. Version auf **1.1.0** setzen, Changelog, Tag  

---

## Erfolgsbedingungen

- [ ] Jede YAML-Regel hat `source` + `id`
- [ ] Keine YAML-only-Pflichtregel
- [ ] README erklärt Konfliktregel (Markdown gewinnt)
- [ ] 1.0-Projekte ohne `rules/` bleiben gültig
- [ ] Mindestens ein Desk- oder Sync-Check dokumentiert

---

## Risiken

| Risiko | Mitigation |
|--------|------------|
| Drift Markdown ↔ YAML | Sync-Pflicht + Check in Release-Checkliste |
| Zu feingranulares Schema | Erst Minimalmodell, später erweitern |
| Tool-Lock-in | Keine Cursor-/Copilot-only-Felder im Core-YAML |
