# AI-DK I18N / Nutzertexte

Version: 1.0.0

## Ziel

Nutzersichtbare Texte liegen **zentral in Ressourcen** und werden im Code nur über **benannte Zugriffs-APIs** gelesen.

Das gilt **technologieunabhängig** und soll sicherstellen:

- konsistente Formulierungen
- einfache Mehrsprachigkeit ohne UI-Umbau
- Review von Copy unabhängig vom Layout
- gleiche Arbeitsweise in jedem Stack und jedem späteren Profile

Profile konkretisieren den Mechanismus (z. B. Flutter `gen-l10n`); sie ersetzen dieses Dokument nicht.

---

## Geltungsbereich

Gilt für:

- nutzersichtbare Texte in UI / Präsentation (Titel, Labels, Buttons, Hinweise, Dialoge, Tooltips, Empty States, Fehlermeldungen an Nutzer)
- neue und geänderte UI-Stellen
- Code Reviews durch die KI

Gilt **nicht** für:

- Domänendaten aus Persistenz oder APIs (Namen, Codes, Rohtexte als Daten)
- vom Nutzer eingegebene Freitexte
- rein interne Developer-Logs, Asserts, Debug-Ausgaben
- technische Exception-Messages, die nie in der UI landen
- stabile technische IDs, Route-Namen, Preference-Keys

Kanonische Zuständigkeit gemäß Matrix in `00_PROJECT_CHARTER.md`.  
Stackspezifische Mechanismen: aktives Profile (z. B. `profiles/flutter/I18N.md`).

Dieses Dokument ist technologie- und modellunabhängig.

---

## Grundprinzipien

### Ein Katalog, viele Aufrufe

String-Literale nicht über UI-Code streuen. Copy lebt in dedizierten Ressourcen-Dateien.

### API statt Literal

UI und Hilfsfunktionen rufen benannte Getter/Methoden/Keys auf — nicht Rohliterale `'…'` / `"…"`.

### Mehrsprachigkeit vorbereiten

Neue Texte so anlegen, dass eine weitere Locale nur Ressourcen braucht, keinen strukturellen Code-Umbau.

### Daten ≠ Copy

Server-, DB- und Import-Inhalte bleiben Daten. Der UI-Rahmen (Labels, Fehlermeldungen, Buttons) kommt aus dem Katalog.

---

## Verbindliche Regeln

### Zentrale Ressourcen

1. Nutzersichtbare Texte liegen in einem **projektweit festgelegten** Ressourcenort (eine oder wenige Katalog-/Locale-Dateien — nicht verstreut in Views/Widgets/Screens).
2. Mindestens eine Template-/Default-Locale ist definiert und dokumentiert (Projektstand oder README).
3. Der gewählte Mechanismus (Framework-L10n, Ressourcen-Dateien, generierte API, …) ist **ein** System — kein paralleles zweites ohne Stand-Eintrag.

### Zugriff im Code

1. UI-Code verwendet nur die projektweite Zugriffs-API (z. B. `t('key')`, `l10n.save`, `strings.cardEditorTitle`).
2. Keine neuen Nutzer-Strings als Literale direkt in UI-Konstruktoren, Templates oder View-Bindings.
3. Parameterisierte Texte über Platzhalter des L10n-/Katalog-Systems — keine Satz-Bastelei, wenn das System Platzhalter bietet.
4. Hilfsfunktionen dürfen Copy kapseln, solange die **Wörter** aus dem Katalog kommen.

### Übergang / Altcode

Wenn der kanonische Mechanismus des Stacks noch nicht verdrahtet ist:

1. **Erlaubt:** ein **zentraler** Übergangskatalog (eine Datei oder eng begrenzte Feature-Kataloge) mit Gettern/Keys.
2. **Verboten:** weiter hardcodierte Nutzer-Strings „nur für jetzt“ in neuem UI-Code.
3. Migration zum kanonischen Mechanismus und Restschuld im Projektstand festhalten.

### Profile und Stack

- Profiles **müssen** dieses Core-Dokument respektieren und dürfen nur Mechanismus, Dateipfade und Generatoren konkretisieren.
- Bei Konflikt: **Core gewinnt** für die Prinzipien; Profile für Tool-/Paketdetails (`profiles/README.md`).

---

## Empfehlungen

- Keys sprechend und stabil halten (`deckStatsManaCurve`, nicht `text17`).
- Gleiche Bedeutung = gleicher Key.
- Locale-Wechsel und Fallback-Verhalten kurz im Projektstand festhalten.
- Bei Berührung bestehender Literale: Boy Scout in den Katalog ziehen, soweit der Aufgabenumfang es zulässt.

---

## KI-Verhalten

Die KI muss:

1. Bei neuem Nutzertext zuerst die Ressource/den Katalog erweitern, dann den Aufruf im UI-Code einbauen.
2. Kein zweites i18n-System neben dem projektdefinierten einführen ohne Stand-Eintrag.
3. Domänendaten nicht fälschlich als UI-Copy in den Katalog spiegeln.
4. Stackspezifische Details dem aktiven Profile entnehmen, ohne Core-Prinzipien zu umgehen.
5. Bestehende Literale bei Berührung der Stelle nachziehen oder als Restschuld benennen.

---

## Checkliste

- [ ] Neuer Nutzer-Text steht in Ressource/Katalog, nicht als Literal in der UI
- [ ] UI nutzt die projektweite Zugriffs-API
- [ ] Kanonischer Mechanismus verdrahtet **oder** dokumentierter Übergangskatalog
- [ ] Kein paralleles i18n-System ohne Stand-Eintrag
- [ ] Domänendaten nicht als Copy missbraucht
- [ ] Profile-Details (falls aktiv) beachtet

---

## Beispiele

### Gut (prinzipiell)

```text
Ressource: cardEditor.newTitle = "Neue Karte"
UI:        text(l10n.cardEditorNewTitle)   // oder t('cardEditor.newTitle')
```

### Gut (Übergangskatalog)

```text
app_strings.get('cardEditor.newTitle')
```

### Schlecht

```text
Text("Neue Karte")          // Literal in der UI
title = id == null ? "Neu" : "Bearbeiten"   // Copy im Screen/Controller
```

---

## Ausnahmen

- Prototyp-UI hinter Feature-Flag: Literale nur mit expliziter, zeitlich begrenzter Stand-Notiz.
- Vendor-/Dritt-UI außerhalb der App-Kontrolle.
- Test-Fixtures dürfen feste Strings nutzen; produktive UI-Pfade trotzdem über Katalog/L10n, wenn der Test Copy prüft.

Sicherheits- oder Korrektheitsanforderungen haben Vorrang vor Copy-Präferenzen.
